# Web eID service contract

`nabu.utils.WebEid.validate(WebEidRequest request)` returns `WebEidResult`. The browser supplies only `tokenJson`, a JSON object containing exactly four string fields: `format`, `algorithm`, `unverifiedCertificate`, `signature`. Missing, duplicate, extra, or wrong-type fields are rejected. Only `web-eid:1.0` and `RS256` are supported. A malformed token returns `valid=false, reason=INVALID_RESPONSE`; a failed certificate/proof/status check returns `valid=false, reason=VERIFICATION_FAILED`. Missing server configuration and OCSP network failures throw, never silently succeed.

The server must supply `challenge` (the original exact opaque 44-128 character string), `origin` (the exact configured HTTPS ASCII site origin), `issuerCertificate` (a standard Java `java.security.cert.Certificate` object containing a directly issuing, explicitly trusted `X509Certificate`), `allowedPolicies` (explicit authentication certificate policy OIDs), and `ocspEndpoint` (a configured nonce-capable responder URL). Do not derive these from browser input, token contents or certificate AIA. The caller selects trust explicitly; this service does not resolve keystore aliases or treat a private-key entry as trusted. A caller using `nabu.misc.keystore.Services.getCertificate(keystoreId, certificateAlias)` must select a trusted certificate entry. `getCertificateChain(keystoreId, keyAlias)` returns the X.509 chain of a private-key entry, not an implicit trust anchor. Both accessors reject missing keystores and wrong or missing alias types with `IllegalArgumentException`, and return standard Java X.509 objects. Keep the responder URL and network access restricted to trusted destinations. OCSP is mandatory by default. Only server-owned deployment policy may set `offlinePolicy=true`; in that mode the result is `NOT_CHECKED`, not `GOOD`. An OCSP network failure is an operational exception, not a validation verdict.

On success the result contains the verified certificate's subject, issuer, hex serial number, ISO-8601 UTC validity dates, base64 DER certificate, `ocspStatus` (`GOOD` or `NOT_CHECKED`), and raw `ocspResponse` bytes when checked. The service does not issue challenges or manage sessions. The caller must generate unpredictable challenges with at least 256 bits of entropy, bind them to the browser session, enforce expiry, and atomically consume them; a valid signature alone does not prevent replay. The verifier supports direct issuers and nonce-capable configured responders only; it does not claim compatibility with all national eID certificates, indirect chains or nonce-less OCSP services. Confirm real certificate policies, direct issuer, and responder behavior before integration.
